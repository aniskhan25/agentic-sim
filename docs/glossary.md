# Glossary

Terms used across `docs/research_roadmap.md`, `docs/target_architecture.md`, and `docs/evaluation_plan.md`, defined against what they mean in the current code today — not as aspirational architecture. Where the roadmap's term differs from the name already used in code, both are given.

**Event** — an `Event` (`models/event.py`): something that happened in the simulation (an environment transition, a message delivery, a scenario trigger). Carries `event_type`, `target_scope`, `payload`, `priority`, and `correlation_id`. Events are routed by role or agent ID via `target_scope`, and drive which agents get a chance to act each tick.

**Activation** — an `Activation` (`models/execution.py:16-22`): one agent's opportunity to act in response to one triggering event. Fields: `activation_id`, `agent_id`, `trigger_event_id`, `activation_reason`, `priority`, `ready_at`, `attempt_number`. `FIFOScheduler` decides which activations exist each tick from ready events and the agent roster.

**Proposal** — the raw structure parsed from a backend's output before validation or policy completion: the `proposal` dict inside `AittaExecutionBackend._try_parse`/`_result_from_proposal` (`execution/aitta_backend.py`). May be marked `model_output_invalid` if it couldn't be parsed as JSON after extraction and repair.

**Validated result** — the proposal after (a) schema parsing into typed `Message`/`EnvironmentAction` objects (`_messages`/`_environment_actions` in `aitta_backend.py`, which reject malformed shapes) and (b) semantic validation against the role's contract (`role_policy.semantic_violations`, `execution/role_policy.py`). Today this is tracked as metadata fields (`semantic_valid`, `must_not_violations`), not yet a dedicated typed object — defining that type is Phase 1 item 3 of the roadmap.

**Commit** — persisting one activation's effects into simulation state via `RuntimeStore.commit(CommitUnit)` (`state/base.py`, `models/commit.py`): the agent's state mutation, its outgoing messages, and its emitted events, applied all-or-nothing and guarded by an idempotency check (`activation_id`) and an optimistic state-version conflict check (`expected_state_version`). Both `InMemoryStateStore` and `SQLiteStateStore` implement it identically (`tests/test_commit_conformance.py`); for SQLite it is a real transaction (`with self.conn:`), not just a convention. Environment mutation (`environment.apply_actions` + `store.environment.put`) remains a separate, tick-level batched step outside this atomic unit — see `docs/research_roadmap.md` item 10's notes for why.

**Policy completion** — what the code and tests call the "policy guard": `role_policy.ensure_required_messages`/`ensure_required_actions` (`execution/role_policy.py`), tracked via the `policy_guard_added_messages`/`policy_guard_added_actions` metadata fields. Deterministically fills in any required message or environment action the model's proposal omitted, computed from ground-truth request data, never from the model's output.

**Fallback** — what happens when a proposal is unusable even after extraction and the bounded re-prompt retry: the backend substitutes a stub proposal (`{"metadata": {"model_output_invalid": True, ...}}`, `_try_parse` in `aitta_backend.py`) and policy completion supplies all required behavior. Tracked via `model_output_invalid`.

**Useful agent step** — a committed activation whose final result satisfies its contracts (zero `must_not` violations, every `must` requirement present). Approximated today by the `useful_step` metadata field (`aitta_backend.py`), aggregated into `useful_agent_steps_per_second` in `_backend_metrics`/`aggregate_run_stats` (`observability/artifacts.py`) using `simulation_tick` trace wall-clock time, not summed per-step latency.

**Dispatch** — submitting one `ExecutionRequest` to a provider and later collecting its result, via `AsyncExecutionBackend.submit()`/`poll()` (`execution/async_backend.py`, `models/dispatch.py`). Distinct from `commit`: dispatch produces a `DispatchOutcome` (`PENDING`/`COMPLETED`/`FAILED`/`CANCELLED`), commit is what happens to a completed result afterward. Today's only implementation is `SynchronousProviderAdapter` (`execution/sync_provider_adapter.py`), which wraps any existing `ExecutionBackend.run_batch`-based backend so it satisfies this port without changing its internals — `submit()` blocks until the whole call finishes, so `PENDING` and a real mid-flight `cancel()` are never observed through it; both are reserved for a future genuinely non-blocking adapter. `SimulationEngine.step()` uses `run_batch` directly by default (`dispatch_policy=None`); when a `dispatch_policy` is set it dispatches through this port instead — see **Dispatch policy**.

**Dispatch policy** — decides the order/concurrency in which one tick's already-scheduled requests are dispatched (`scheduling/dispatch_policy.py`'s `DispatchPolicy` Protocol), on top of the unmodified `FIFOScheduler` (still one activation per agent per tick — this is not a scheduling-policy change). The full 7-rung ladder: `SequentialDispatchPolicy` (one at a time, the deterministic reference), `NaiveConcurrentDispatchPolicy` (a real `ThreadPoolExecutor`, no conflict protection — the negative control), `BarrierDispatchPolicy` (concurrent within each `BatchBuilder` backend-hint group, but waits for one group to finish before the next), `CausalOnlyDispatchPolicy` (concurrent within message-causally-independent waves computed by `build_causal_waves`, strictly ordered across waves), `CapabilityAwareDispatchPolicy` (rung 5: within each wave, groups by `backend_hint` and only dispatches a group concurrently if `backend.capabilities.supports_concurrency` — rungs 1-4 ignore this signal entirely), `QueueAwareDispatchPolicy` (rung 6: same, but caps each group's concurrency at a configurable per-`backend_hint` max-in-flight limit — real, bounded backpressure via a smaller `ThreadPoolExecutor` worker count, not an uncapped one), `FullDispatchPolicy` (rung 7: same, plus sub-grouping by `agent_profile.role` as a proxy for reusable-prefix similarity, since no backend declares `supports_prefix_caching` today). `SimulationEngine(dispatch_policy=...)` opts into this path for any of the seven; `None` (the default) preserves the original `run_batch` loop exactly. All seven are scoped to message-mediated causal ordering only (same scope as the causal verifier) — none protect against environment-level conflicts (e.g. the synthetic kernel's `conflicting_write` shape). Because message-mediated causal chains always span at least one tick boundary in this engine's model, all seven rungs collapse to identical behavior on every scenario that exists today regardless of `backend_hint`/role heterogeneity (item 15 added `provider_count`/`role_count` heterogeneity to the synthetic kernel — see **Workload suite** — but heterogeneity alone doesn't change wave structure, only grouping); each rung's distinguishing mechanism is nonetheless correct and independently verified via hand-built heterogeneous fixtures (mixed `backend_hint`, mixed role, mixed capabilities) in `tests/test_dispatch_policies.py`.

**Provider error** — a dispatch failure normalized into one of a small set of provider-neutral categories (`execution/errors.py`: `ProviderError` and its subtypes `ProviderTimeoutError`, `ProviderCapacityError`, `ProviderCancelledError`, `ProviderUnsupportedCapabilityError`, `ProviderMalformedResponseError`), surfaced via `DispatchOutcome.error` rather than raised from `submit()`/`poll()`. Only `ProviderTimeoutError` and the generic `ProviderError` catch-all are actually produced by classification logic today; the other subtypes exist for the taxonomy's completeness and for a future backend to raise directly.

**Workload suite** — `evaluation_plan.md`'s Publication Suite: five workload families (deterministic kernel, storm coordination, supply-chain coordination, synthetic dependency graphs, failure workloads) swept across dimensions. As of item 15, the synthetic kernel (`scenarios/synthetic.py`) supports `conflict_ratio` on the `conflicting_write` shape (a continuous partial-conflict dimension; default `1.0` reproduces the original all-conflict behavior exactly, since conflict is an environment-write property and leaves `expected_invariants` unchanged regardless of ratio) and `provider_count`/`role_count` (round-robin `backend_hint`/role heterogeneity across every shape's roster; default `1`/`1` reproduces the original uniform `backend="mock"`/`role="synthetic_node"` exactly, since `SyntheticExecutionBackend` branches only on `agent_id`, never on these labels — provably inert to simulation behavior, verified by the same `graph_metrics`/`verify()` equivalence checks used throughout). **Failure injection** (below) fills the one entirely-missing required family. Input/output length distributions and logical deadline tightness remain unbuilt — no field for either exists anywhere, and neither has a consumer yet, matching the same "don't build unexercised fields" discipline applied to `deadline` in earlier items.

**Failure injection** — `execution/failure_injecting_backend.py::FailureInjectingBackend`, a real `ExecutionBackend` wrapper implementing `evaluation_plan.md`'s "failure workloads" dimension: `"timeout"` raises `TimeoutError`, `"malformed"` returns a normal, committable `ExecutionResult` flagged `metadata={"model_output_invalid": True}` (mirroring `AittaExecutionBackend`'s real fallback semantics), `"interruption"` raises a generic exception. Failure selection is deterministic — either an explicit per-agent `failure_plan` or an index-cycling `cycle` list, never RNG, matching this codebase's "seeded means deterministic" convention throughout. Wired into `create_synthetic_engine` via an optional `scenario_parameters["failure_injection"]` config. Only meaningfully non-crashing through the dispatch-policy path (**Dispatch policy** above): `SynchronousProviderAdapter.submit()` catches the raised exception and converts it to `DispatchOutcome(status=FAILED, error=...)`; using this backend as `SimulationEngine.backend` with `dispatch_policy=None` propagates the exception and crashes the run, exactly like any other failing backend would — not a gap, the existing correct behavior. "Duplicate response" (the fourth failure type `evaluation_plan.md` names) is deliberately not reimplemented here — `tests/test_commit_conformance.py` (item 10) already directly tests duplicate-`activation_id` handling at the commit layer.

**Platform telemetry collector** — `observability/base.py::TelemetryCollector` (item 16), a Protocol (`collect() -> list[PlatformTelemetrySample]`) kept deliberately separate from the existing **Telemetry** port above: `Telemetry.record_event` is a generic sink already wired into `SimulationEngine`'s `agent_step`/`simulation_tick` bookkeeping; `TelemetryCollector` is a typed GPU-specific source. `models/platform_telemetry.py::PlatformTelemetrySample` is the one provider-neutral schema `evaluation_plan.md`'s "Platform telemetry" section calls for (GPU utilization, HBM used/total, GPU power, energy, host CPU utilization), every field defaulting to `None` per its "missing telemetry is explicit rather than imputed" — `kv_cache_used_percent`/`preemption_count`/`queue_depth` exist in the schema but stay unpopulated pending a future serving-runtime (vLLM `/metrics`) collector, out of this item's ROCm/CUDA-only scope. `RocmTelemetryCollector`/`CudaTelemetryCollector` (`observability/rocm_collector.py`/`cuda_collector.py`) shell out to `rocm-smi`/`nvidia-smi` through an injectable `CommandRunner` seam (mirroring `OpenAICompatibleExecutionBackend`'s `Transport` callable), turning any collection failure into a single `error`-bearing sample rather than a crash. `SimulationEngine`'s optional `telemetry_collector` constructor arg defaults to `None` (zero behavior change for every existing caller) and is polled once per tick when configured — a sample only ever reaches the trace store via `Telemetry.record_event`, never affecting scheduling (`target_architecture.md` Rule 6). `observability/artifacts.py::_platform_telemetry` aggregates samples into a new `platform_telemetry.json` per-run artifact, mirroring `_backend_metrics`'s exact shape. Selectable via `--platform-telemetry {rocm,cuda}` / `"execution": {"platform_telemetry": "rocm"}`. `docs/adr/0002-runtime-owned-telemetry-collection-port.md` records the port-split and schema decisions. Tested entirely against fixture text and fake runners — neither collector has run against real ROCm/CUDA hardware, since none exists in this session.

**Self-hosted backend** — `execution/self_hosted_backend.py::SelfHostedExecutionBackend` (item 19), the prerequisite for real LUMI/Roihu deployment (`docs/lumi_deployment_manifest.md`). An OpenAI-compatible client sharing every request/response/repair/role-policy/receipt behavior with `AittaExecutionBackend` via a new shared base, `execution/openai_compatible_backend.py::OpenAICompatibleExecutionBackend` — extracted verbatim from `AittaExecutionBackend` (confirmed fully generic, zero Aitta-specific assumptions, by direct line-by-line reading before extraction; `test_aitta_backend.py`'s full suite passes unchanged, proving the extraction is behavior-preserving). Differs from Aitta in exactly what's genuinely different about a self-hosted deployment: no required API key (`SELF_HOSTED_API_KEY` is optional — the base class's `_send` omits the `Authorization` header entirely when `api_key` is empty, identical behavior for Aitta since its required-ness check already guarantees a truthy key), and configurable `enable_prefix_caching`/`max_context_tokens` (a real deployment knows its own `vllm serve` flags; Aitta can't know the upstream managed service's). Selectable via `--backend self_hosted` / `"execution": {"backend": "self_hosted"}`, with a `check-self-hosted --wait` health-check mirroring `check-aitta --wait`. Closes ADR 0005's stated gap for the first time: the base class accepts an optional `platform_manifest: PlatformManifest | None`, and when one is configured, every produced `ExecutionReceipt` carries `accelerator`/`host_architecture`/`serving_runtime` (previously dormant fields, never populated by any code path) and the new `manifest_mode` field — non-`None` is what ADR 0005 defines as marking a run as primary performance evidence rather than a portability observation. Tested entirely against a fake transport, exactly like `AittaExecutionBackend` always has been — it has never run against a real vLLM server, since no self-hosted deployment exists yet.
