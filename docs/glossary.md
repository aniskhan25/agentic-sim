# Glossary

Terms used across `docs/research_roadmap.md`, `docs/target_architecture.md`, and `docs/evaluation_plan.md`, defined against what they mean in the current code today — not as aspirational architecture. Where the roadmap's term differs from the name already used in code, both are given.

**Event** — an `Event` (`models/event.py`): something that happened in the simulation (an environment transition, a message delivery, a scenario trigger). Carries `event_type`, `target_scope`, `payload`, `priority`, and `correlation_id`. Events are routed by role or agent ID via `target_scope`, and drive which agents get a chance to act each tick.

**Activation** — an `Activation` (`models/execution.py:16-22`): one agent's opportunity to act in response to one triggering event. Fields: `activation_id`, `agent_id`, `trigger_event_id`, `activation_reason`, `priority`, `ready_at`, `attempt_number`. `FIFOScheduler` decides which activations exist each tick from ready events and the agent roster.

**Proposal** — the raw structure parsed from a backend's output before validation or policy completion: the `proposal` dict inside `AittaExecutionBackend._try_parse`/`_result_from_proposal` (`execution/aitta_backend.py`). May be marked `model_output_invalid` if it couldn't be parsed as JSON after extraction and repair.

**Validated result** — the proposal after (a) schema parsing into typed `Message`/`EnvironmentAction` objects (`_messages`/`_environment_actions` in `aitta_backend.py`, which reject malformed shapes) and (b) semantic validation against the role's contract (`role_policy.semantic_violations`, `execution/role_policy.py`). Today this is tracked as metadata fields (`semantic_valid`, `must_not_violations`), not yet a dedicated typed object — defining that type is Phase 1 item 3 of the roadmap.

**Commit** — persisting one activation's effects into simulation state via `RuntimeStore.commit(CommitUnit)` (`state/base.py`, `models/commit.py`): the agent's state mutation, its outgoing messages, and its emitted events, applied all-or-nothing and guarded by an idempotency check (`activation_id`) and an optimistic state-version conflict check (`expected_state_version`). Both `InMemoryStateStore` and `SQLiteStateStore` implement it identically (`tests/test_commit_conformance.py`); for SQLite it is a real transaction (`with self.conn:`), not just a convention. Environment mutation (`environment.apply_actions` + `store.environment.put`) remains a separate, tick-level batched step outside this atomic unit — see `docs/research_roadmap.md` item 10's notes for why.

**Policy completion** — what the code and tests call the "policy guard": `role_policy.ensure_required_messages`/`ensure_required_actions` (`execution/role_policy.py`), tracked via the `policy_guard_added_messages`/`policy_guard_added_actions` metadata fields. Deterministically fills in any required message or environment action the model's proposal omitted, computed from ground-truth request data, never from the model's output.

**Fallback** — what happens when a proposal is unusable even after extraction and the bounded re-prompt retry: the backend substitutes a stub proposal (`{"metadata": {"model_output_invalid": True, ...}}`, `_try_parse` in `aitta_backend.py`) and policy completion supplies all required behavior. Tracked via `model_output_invalid`.

**Useful agent step** — a committed activation whose final result satisfies its contracts (zero `must_not` violations, every `must` requirement present). Approximated today by the `useful_step` metadata field (`aitta_backend.py`), aggregated into `useful_agent_steps_per_second` in `_backend_metrics`/`aggregate_run_stats` (`observability/artifacts.py`) using `simulation_tick` trace wall-clock time, not summed per-step latency.

**Dispatch** — submitting one `ExecutionRequest` to a provider and later collecting its result, via `AsyncExecutionBackend.submit()`/`poll()` (`execution/async_backend.py`, `models/dispatch.py`). Distinct from `commit`: dispatch produces a `DispatchOutcome` (`PENDING`/`COMPLETED`/`FAILED`/`CANCELLED`), commit is what happens to a completed result afterward. Today's only implementation is `SynchronousProviderAdapter` (`execution/sync_provider_adapter.py`), which wraps any existing `ExecutionBackend.run_batch`-based backend so it satisfies this port without changing its internals — `submit()` blocks until the whole call finishes, so `PENDING` and a real mid-flight `cancel()` are never observed through it; both are reserved for a future genuinely non-blocking adapter. `SimulationEngine.step()` uses `run_batch` directly by default (`dispatch_policy=None`); when a `dispatch_policy` is set it dispatches through this port instead — see **Dispatch policy**.

**Dispatch policy** — decides the order/concurrency in which one tick's already-scheduled requests are dispatched (`scheduling/dispatch_policy.py`'s `DispatchPolicy` Protocol), on top of the unmodified `FIFOScheduler` (still one activation per agent per tick — this is not a scheduling-policy change). Four baselines: `SequentialDispatchPolicy` (one at a time, the deterministic reference), `NaiveConcurrentDispatchPolicy` (a real `ThreadPoolExecutor`, no conflict protection — the negative control), `BarrierDispatchPolicy` (concurrent within each `BatchBuilder` backend-hint group, but waits for one group to finish before the next), `CausalOnlyDispatchPolicy` (concurrent within message-causally-independent waves, strictly ordered across waves). `SimulationEngine(dispatch_policy=...)` opts into this path; `None` (the default) preserves the original `run_batch` loop exactly. Scoped to message-mediated causal ordering only (same scope as the causal verifier) — provides no protection against environment-level conflicts (e.g. the synthetic kernel's `conflicting_write` shape). Because message-mediated causal chains always span at least one tick boundary in this engine's model, causal-only and naive-concurrent produce identical (single-wave) behavior on every scenario that exists today; the wave-building logic is still independently correct, verified by direct construction of an artificial in-batch dependency (`tests/test_dispatch_policies.py`).

**Provider error** — a dispatch failure normalized into one of a small set of provider-neutral categories (`execution/errors.py`: `ProviderError` and its subtypes `ProviderTimeoutError`, `ProviderCapacityError`, `ProviderCancelledError`, `ProviderUnsupportedCapabilityError`, `ProviderMalformedResponseError`), surfaced via `DispatchOutcome.error` rather than raised from `submit()`/`poll()`. Only `ProviderTimeoutError` and the generic `ProviderError` catch-all are actually produced by classification logic today; the other subtypes exist for the taxonomy's completeness and for a future backend to raise directly.
