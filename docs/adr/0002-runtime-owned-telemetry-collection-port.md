# ADR 0002: Runtime-Owned Telemetry Collection Port

## Status

Proposed.

## Context and Forces

`docs/adr/README.md` has listed ADR 0002 as "Runtime-owned provider, store, clock, and telemetry ports" since this repo's earliest ADR planning, status Proposed, but no file existed for it — the provider (`ExecutionBackend`), store (`RuntimeStore`), and clock (`Clock`) ports were built and adopted without a dedicated ADR because none of them made a genuinely contested shape decision worth recording; `Telemetry` (`observability/base.py`) likewise shipped (commit b288135) as an uncontested single-method `Protocol` (`record_event(event_name, payload)`), wired into `SimulationEngine` for generic `agent_step`/`simulation_tick` bookkeeping. This ADR does not retroactively relitigate those three settled ports. It exists because roadmap item 16 ("Add provider-neutral telemetry with ROCm and CUDA collectors," per `docs/evaluation_plan.md`'s "Platform telemetry" section) introduces genuinely new, binding shape and boundary decisions that the existing `Telemetry` port's simplicity does not answer on its own — the same kind of decision ADR 0005 was written to record for `PlatformManifest`.

`evaluation_plan.md`'s Platform telemetry section requires "one provider-neutral schema populated by: ROCm and available `rocm-smi` or LUMI energy metrics; CUDA and available `nvidia-smi` or Roihu scheduler accounting; serving-runtime request and KV-cache metrics; application execution receipts... Record GPU utilization, HBM use, KV-cache use, preemption, host utilization, queueing, and energy when observable. Missing telemetry is explicit rather than imputed." `docs/target_architecture.md` gives two binding constraints regardless of design specifics: Architectural Rule 6 ("Telemetry observes. Metrics do not affect behavior unless routed explicitly through a typed scheduling-policy input.") and a Change-Isolation Requirement naming exactly this item's goal: "adding ROCm or CUDA telemetry without changing simulation results."

Neither existing platform-adjacent typed record fits a periodic-sample shape: `PlatformManifest` is a static, one-shot hardware/software descriptor built once per deployment; `ExecutionReceipt` is a one-shot per-activation-attempt record. No GPU hardware exists in this session to validate against (confirmed: no `nvidia-smi`/`rocm-smi` on this development machine; the live Roihu SSH session used for `docs/roihu_deployment_manifest.md` only reached a GPU-less login node) — any collector design must be testable without real hardware present.

## Decision

**A new `PlatformTelemetrySample` dataclass** (`models/platform_telemetry.py`), not an extension of `PlatformManifest` or `ExecutionReceipt`, holds one periodic snapshot: `collected_at`, `source`, `accelerator_index`, `gpu_utilization_percent`, `hbm_used_mb`, `hbm_total_mb`, `gpu_power_watts`, `energy_joules`, `host_cpu_utilization_percent`, `kv_cache_used_percent`, `preemption_count`, `queue_depth`, `error`. One shared schema is used across both vendors rather than per-vendor dataclasses, per `evaluation_plan.md`'s own "one provider-neutral schema" wording. Every live-metric field defaults to `None` — matching `PlatformManifest`/`ExecutionReceipt`'s established "missing telemetry is explicit rather than imputed" discipline — and `error` is kept distinct from a `None` field: `None` means "this source doesn't expose this metric," `error` means "the collector could not run at all" (binary missing, timeout), never silently swallowed.

**`kv_cache_used_percent`/`preemption_count`/`queue_depth` are part of the schema but unpopulated by design in this phase.** They exist because `evaluation_plan.md` names serving-runtime request/KV-cache metrics as a required telemetry source, but item 16's title scopes this build to ROCm/CUDA collectors only. A future serving-runtime collector (e.g. scraping vLLM's `/metrics` endpoint) populates them later without changing this schema.

**A new `TelemetryCollector` Protocol** (`observability/base.py`, `collect(self) -> list[PlatformTelemetrySample]`), kept separate from the existing `Telemetry` Protocol. `Telemetry.record_event` is a generic sink already wired everywhere; `TelemetryCollector.collect` is a typed GPU-specific source. Conflating them would either pollute `Telemetry`'s signature with GPU-specific concerns or make `record_event` double as a poll trigger. A collected sample only ever reaches the engine through `Telemetry.record_event` — it never affects scheduling or control flow, satisfying Rule 6 and the Change-Isolation requirement directly, since `SimulationEngine.step()`'s committed behavior is identical whether `telemetry_collector` is `None` or returns real samples.

**Two concrete collectors**, `RocmTelemetryCollector`/`CudaTelemetryCollector` (`observability/rocm_collector.py`/`cuda_collector.py`), shell out to `rocm-smi --showuse --showmeminfo vram --showpower --json` / `nvidia-smi --query-gpu=...,--format=csv,noheader,nounits` respectively. An injectable `CommandRunner = Callable[[list[str], float], str]` seam (mirroring `OpenAICompatibleExecutionBackend`'s `Transport` callable) lets both be unit-tested against fixture text without the real binary present; any collection failure (missing binary, timeout, malformed output) is caught and returned as a single `error`-bearing sample rather than raised, so a broken telemetry source degrades a run's evidence quality without ever crashing it. Fixture shapes are based on public `rocm-smi`/`nvidia-smi` documentation and are explicitly not verified against real hardware output in this session.

**Engine wiring is additive, optional, and per-tick.** `SimulationEngine` gains `telemetry_collector: TelemetryCollector | None = None`, defaulting to `None` (zero behavior change for every existing caller), and calls `.collect()` once per tick alongside the existing `simulation_tick` event when a collector is configured. Per-tick rather than once-per-run: utilization/HBM/power genuinely vary tick to tick under real backend load, and a per-tick sample can be joined against `backend_metrics.json`'s per-tick timings later. No interval-throttling knob is added — no evidence yet that per-tick collection overhead is a real problem, and it is an easy, non-breaking follow-up if HPC runs later show otherwise.

**LUMI job-energy accounting and Roihu SLURM scheduler-accounting are deferred**, not built in this phase — both are named as alternative sources in `evaluation_plan.md`'s bullets 1-2, but both need a live cluster to shape correctly, unlike the two collectors' stable public CLI-tool output. `energy_joules` stays `None` from both collectors until that follow-up exists.

## Alternatives Considered

- **Extending `PlatformManifest` with live-metric fields.** Rejected: `PlatformManifest` is constructed once per deployment and describes static identity; bolting periodic-sample fields onto it would leave most of them unpopulated on the vast majority of manifest instances and conflate two different lifetimes (once-per-deployment vs. once-per-tick).
- **Reusing `Telemetry.record_event` as the collection trigger** (e.g. a `record_event("collect_platform_telemetry", {})` call that some listener intercepts). Rejected: this repurposes a sink as a control signal, inverting the port's existing, simple, already-tested meaning, and would make substitutability (`FakeTelemetry`) ambiguous about whether it's expected to also emulate collection side effects.
- **A single `GpuTelemetryCollector` with vendor branching inside `collect()`** instead of two classes. Rejected: `rocm-smi`/`nvidia-smi` have unrelated CLI syntaxes and output shapes; one collector class branching internally would need the same amount of vendor-specific code as two classes, with less clarity about which vendor is actually active for a given deployment.
- **Building a third, serving-runtime (vLLM `/metrics`) collector now**, to fully populate the shared schema immediately. Rejected: out of this item's stated scope (its title names only ROCm/CUDA collectors); deferred as documented future work rather than scope-creeping into a third collector type this pass.

## Consequences

- `docs/glossary.md` and `docs/research_roadmap.md`'s item 16 entry are expected to describe telemetry collection in terms of `PlatformTelemetrySample`/`TelemetryCollector`, not ad hoc prose.
- `kv_cache_used_percent`/`preemption_count`/`queue_depth`/`energy_joules` remain `None` in every `platform_telemetry.json` artifact produced today — this is correct, not a bug, until a serving-runtime collector and cluster-accounting collectors are built.
- Any future serving-runtime or scheduler-accounting collector must populate the same `PlatformTelemetrySample` shape, not invent a parallel one.
- Neither collector has been run against real ROCm/CUDA hardware — this ADR records the target shape and port boundary; it does not claim hardware validation that hasn't happened.
- This is Proposed, not Accepted — accepting it is a separate, explicit decision, matching ADR 0005's own precedent.

## Conformance / Verification Method

`tests/test_rocm_collector.py`/`tests/test_cuda_collector.py` verify the parser functions against fixture text and verify collection failures produce an `error`-bearing sample rather than an exception; `tests/test_platform_telemetry.py` verifies the `_platform_telemetry` artifact aggregator's shape, including that unpopulated serving-runtime fields report `count: 0` rather than a fabricated value; `tests/test_engine.py` verifies `telemetry_collector` defaults to `None` with zero behavior change to the pre-existing engine test suite, and that a configured collector is polled exactly once per tick. Conformance to this ADR means: any future telemetry-collection code is expressible in terms of `PlatformTelemetrySample`/`TelemetryCollector` without contradicting the boundaries above, and no collector is ever wired into scheduling or control-flow decisions.
